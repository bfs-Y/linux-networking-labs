DRILL 1 - What is a network namespace, and how is it the same underlying kernel concept as a PID namespace?
YOUR ANSWER:
>
REFERENCE:
A complete, private copy of the network stack - own interfaces, IP, routing table, firewall rules - isolated from the host and other namespaces, all on the same kernel. Same isolation primitive as PID namespaces, applied to networking instead of processes.

DRILL 2 - What role does docker0 play between a container's private namespace and the host's real interface?
YOUR ANSWER:
>
REFERENCE:
docker0 is a virtual switch/bridge on the host side - each container's namespace connects to it via a veth pair. docker0 acts as the container network's gateway (e.g. 172.17.0.1), then forwards traffic through the host's real interface to actually reach the network.

DRILL 3 - You see a container using 172.17.x.x and a VM using 192.168.x.x. Are these fundamentally different types of addressing?
YOUR ANSWER:
>
REFERENCE:
No - both are private, non-internet-routable ranges, just different reserved blocks chosen to avoid collision. The /16 vs /24 changes how much of the address is network vs host, same subnet math either way.

DRILL 4 - Start a container and confirm it received its own private IP inside its own namespace. What two commands?
YOUR ANSWER:
>
REFERENCE:
sudo docker inspect <container> | grep -A 5 '"IPAddress"' - shows the container's private IP.
ip a show docker0 - confirms the bridge came UP with the new attachment.

DRILL 5 - A container can't reach the internet, but the host can. First two checks, and what do they tell you if they pass?
YOUR ANSWER:
>
REFERENCE:
ip a show docker0 - confirms the bridge is UP. curl the container's IP directly from the host - confirms host-to-container connectivity works. If both pass, namespace isolation itself is fine; the problem is elsewhere.

DRILL 6 - Host-to-container connectivity works, but the container still can't reach the internet. Where's the fault, and why isn't it a namespace problem?
YOUR ANSWER:
>
REFERENCE:
NAT/forwarding rules on the host (iptables), not the namespace - the container's isolation and its path IN are proven working; what's broken is specifically the path OUT through the host's NAT/forwarding config.

DRILL 7 - After stopping and removing a test container, what confirms the teardown was actually clean, not just that the container command succeeded?
YOUR ANSWER:
>
REFERENCE:
sudo docker ps -a | grep <container> should return nothing (or explicit "Confirmed clean" check), and ip a show docker0 should show the bridge returning to idle if no other containers remain attached.
