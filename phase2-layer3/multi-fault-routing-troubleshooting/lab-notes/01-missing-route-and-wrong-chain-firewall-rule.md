# Lab Notes -- Multi-Fault Capstone: Missing Return Route + Misplaced Firewall Rule

Date: 2026-08-29

## Objective
Diagnose two simultaneous, independent faults on the same multi-hop
path (client -- router1 -- server) with no prior knowledge of what was
broken, using only the diagnostic toolkit built across earlier Phase 2
labs (ping, tcpdump, ip route, iptables -L).

## Topology
Same 3-namespace path from the mtr-advanced lab:
  client (10.0.1.2/24) -- router1 (10.0.1.1 / 10.0.2.1, forwarding) -- server (10.0.2.2/24)

## Faults Injected (unknown to the investigator at the time)
1. sudo ip netns exec server ip route del 10.0.1.0/24 via 10.0.2.1
   (removed server's only route back to client's subnet)
2. sudo ip netns exec router1 iptables -I OUTPUT 1 -p icmp --icmp-type echo-reply -j DROP
   (a firewall rule placed on the WRONG chain -- see Fault 2 below)

## Investigation, Step by Step

### Symptom
ping -c 3 10.0.2.2 (from client): 100% packet loss, zero replies.

### Step 1 -- Capture at the chokepoint
Ran tcpdump inside router1 (the natural chokepoint every packet must
cross) WHILE reproducing the failure, not after:
  sudo ip netns exec router1 tcpdump -i any -n icmp &
  sudo ip netns exec client ping -c 3 10.0.2.2

Result: echo-request seen arriving from client AND correctly forwarded
out toward server, for all 3 packets. NO echo-reply ever appeared in
the capture, in either direction.

### Step 2 -- Isolate the direction
Outbound (client -> server) proven healthy by the capture. Reply never
reaching router1 at all narrows the fault to something on/near server,
specifically preventing the reply from ever being transmitted.

### Step 3 -- Check server's routing table
sudo ip netns exec server ip route
Result: only the connected 10.0.2.0/24 route present. No route to
10.0.1.0/24 (client's subnet) existed at all.

### Fault 1 Root Cause
With no route to 10.0.1.0/24 and no default route, the kernel's route
lookup for the reply's destination (10.0.1.2) fails outright. The
packet is never transmitted -- not misdirected, never sent at all.
This explains why router1's capture showed nothing: there was nothing
to forward, because server never put a reply onto the wire.

### Fix 1
sudo ip netns exec server ip route add 10.0.1.0/24 via 10.0.2.1

### Step 4 -- Re-test, discover Fault 1 was not the only issue
ping -c 3 10.0.2.2 succeeded immediately, 0% loss, after only Fault 1
was fixed -- meaning Fault 2 (the firewall rule) was present the whole
time but never actually affected this traffic.

### Step 5 -- Investigate why Fault 2 had no observable effect
sudo ip netns exec router1 iptables -L OUTPUT -v -n --line-numbers
Result: the echo-reply DROP rule showed 0 pkts / 0 bytes -- present in
the table, syntactically valid, but never matched by any real traffic.

### Fault 2 Root Cause
The rule targeted router1's OUTPUT chain, which only matches traffic
router1 GENERATES itself. The server's echo-reply is traffic router1
merely RELAYS from server to client -- this passes through the
FORWARD chain, a third, distinct chain from INPUT/OUTPUT that governs
traffic transiting a routing device without being addressed to or
originating from it. A rule on the wrong chain can be completely
correct in syntax and intent, yet functionally inert.

### Fix 2
Removed the ineffective rule (the intended lesson was recognizing
the wrong chain, not building a working replacement):
sudo ip netns exec router1 iptables -D OUTPUT -p icmp --icmp-type echo-reply -j DROP

## Evidence Summary
- tcpdump at the chokepoint proved the outbound path healthy and
  isolated the fault to the return path, before touching any config.
- ip route on server directly showed the missing route -- no
  assumption required.
- iptables -L OUTPUT -v -n --line-numbers with 0 pkts/0 bytes proved
  the second rule was inert BEFORE removing it, avoiding the mistake
  of assuming a present rule is automatically an active rule.

## Real-World Relevance
- Multi-fault incidents are the norm in real production troubleshooting,
  not the exception -- fixing one symptom and declaring victory without
  re-testing is a common, costly mistake.
- A missing return route produces silent, total loss with a healthy-
  looking forward path -- always check routing on BOTH ends of a
  suspected connectivity issue, not just the side initiating traffic.
- On any routing device, iptables rules must target the correct one of
  three distinct chains (INPUT, OUTPUT, FORWARD) depending on whether
  traffic is addressed to the device itself, generated by it, or merely
  passing through it. A rule's mere presence in a chain listing does
  not prove it is having any effect -- always check hit counters
  (pkts/bytes) before trusting that a rule is doing its job.
