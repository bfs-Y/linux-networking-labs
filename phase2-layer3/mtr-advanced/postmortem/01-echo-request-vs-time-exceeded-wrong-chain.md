# Postmortem

Date: 2026-08-23

Lab: Phase 2 -- Advanced MTR: Genuine Multi-Hop Attribution

## Symptom (verbatim command and output)

Command: sudo ip netns exec client mtr -r -c 10 10.0.2.2
(after rate-limiting ICMP echo-request on router1's INPUT chain)
Output:
  1.|-- 10.0.1.1                   0.0%    10
  2.|-- 10.0.2.2                   0.0%    10

Expected some loss at hop 1; observed 0% loss on both hops despite the
rate-limit rule being correctly inserted and verified in position.

## Root Cause

Two compounding mistakes, corrected in sequence:

1. Targeted the wrong ICMP type. mtr/traceroute probe intermediate
   hops using low-TTL packets, which trigger an automatic ICMP
   "time exceeded" (type 11) reply from that hop -- NOT an
   echo-request/echo-reply exchange. A rule matching only
   echo-request (type 8) never sees this traffic at all.

2. After correcting the ICMP type, still targeted the wrong chain
   (INPUT instead of OUTPUT). time-exceeded messages are generated BY
   the router and sent OUT toward the client -- from the router's own
   perspective this is OUTPUT traffic, never INPUT, regardless of
   ICMP type.

## Evidence

- iptables -L INPUT -v -n on router1 showed 0 pkts/0 bytes on the
  echo-request rule even after a full mtr run -- proof the rule was
  never matched.
- tcpdump -i any -n icmp on router1 during an mtr run showed the
  actual traffic: "ICMP time exceeded in-transit" replies, not
  echo-reply -- direct evidence of the real ICMP type involved.
- After correcting to OUTPUT + time-exceeded, iptables -L OUTPUT -v -n
  showed real, nonzero packet counts on both the ACCEPT and DROP
  rules, and mtr showed 10.0% loss on hop 1, 0.0% on hop 2 -- proof
  the corrected rule genuinely matched and rate-limited the intended
  traffic.

## What Changed vs What Stayed the Same

Changed: which ICMP type (echo-request to time-exceeded) and which
chain (INPUT to OUTPUT) the rate-limit rule targeted.

Stayed the same: the underlying network topology (3 namespaces, 2
veth pairs, routing, ip_forward) was correct from the first attempt
and never needed modification -- only the firewall rule itself was
wrong, twice, in two different ways.

## Fix Applied

phase2-layer3/mtr-advanced/fix/01-remove-time-exceeded-limit.sh --
removes the correctly-targeted OUTPUT/time-exceeded rate limit,
restoring normal hop-1 responsiveness.

## Automated or Permanent Version of the Fix

break/01-rate-limit-time-exceeded-on-router.sh builds the full
topology and applies the correct rule from the start, as a reusable,
reproducible lab -- eliminating the need to rediscover the ICMP-type
and chain-direction lessons from scratch each time.

## Detection Gap

Assuming a firewall rule's effect based on ICMP protocol name alone
("it's ICMP, so this rule should affect it") is not sufficient --
ICMP has multiple distinct types serving different purposes, and a
rule written for one type has zero effect on another. Before writing
or debugging any ICMP-related firewall rule, capture real traffic
first (tcpdump -i any -n icmp) to confirm the exact type actually
involved, rather than assuming it matches the tool or command being
used (ping vs traceroute/mtr use different ICMP types entirely).

Separately: when writing a firewall rule intended to affect a host's
own generated responses (not traffic passing through or destined for
it), always confirm whether that traffic is generated locally (OUTPUT)
or arriving from elsewhere (INPUT) before choosing a chain -- these
are easy to conflate, especially for automatic protocol responses like
ICMP time-exceeded that most engineers don't think about as "traffic
this host generates."
