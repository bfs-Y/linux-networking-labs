# Lab Notes -- Advanced MTR: Genuine Multi-Hop Path and ICMP Type Precision

Date: 2026-08-23

## Objective
Build a genuine multi-hop network path (not a simulated single-hop
lab) and use it to correctly attribute loss to a specific intermediate
hop, distinguishing it from loss at the final destination -- and
discover which ICMP type actually needs to be targeted to affect
traceroute/mtr behavior.

## Topology Built
Three network namespaces on the hypervisor, connected by two veth
pairs, forming a genuine two-subnet path:

  client (10.0.1.2/24)
    -- veth-client <-> veth-r1a --
  router1 (10.0.1.1/24 and 10.0.2.1/24, ip_forward=1)
    -- veth-r1b <-> veth-server --
  server (10.0.2.2/24)

client's route to 10.0.2.0/24 goes via router1 (10.0.1.1).
server's route to 10.0.1.0/24 goes via router1 (10.0.2.1).

## Step 1: Prove a Genuine Hop Exists
ping -c 3 10.0.2.2 (from client) succeeded, TTL=63 (not 64) -- direct
proof the packet passed through exactly one real router, since TTL
decrements by 1 per hop.

mtr -r -c 5 10.0.2.2 correctly showed two distinct hops:
  1. 10.0.1.1 (router1)
  2. 10.0.2.2 (server)

## Step 2: First Attempt at Isolating Hop 1 -- Failed, and Why
Applied an ICMP echo-request rate-limit to router1's INPUT chain
(same rule proven to work in the earlier ICMP rate-limit lab). Result:
mtr showed 0% loss on hop 1 -- the rule appeared to have no effect.

Investigated with tcpdump on router1 during an mtr run. Found that
mtr's probes to an INTERMEDIATE hop generate ICMP "time exceeded
in-transit" replies (type 11), NOT "echo reply" (type 0) responses to
an echo-request (type 8). The echo-request rate-limit rule only
matched type 8 traffic -- time-exceeded traffic passed through
untouched, explaining the 0% loss result.

This matters because traceroute/mtr do not ask each intermediate hop
"are you there" the way ping does -- they send low-TTL packets, and
each hop AUTOMATICALLY generates a time-exceeded message as a side
effect of the TTL reaching zero. Rate-limiting echo-request therefore
does nothing to affect traceroute-style probing of that hop.

## Step 3: Second Attempt -- Wrong Chain, Corrected
Time-exceeded messages are GENERATED BY router1 and sent OUT toward
the client -- this is OUTPUT traffic, not INPUT. Applying the rate
limit to INPUT (as with the original echo-request approach) would
never match this traffic regardless of ICMP type, since it never
enters router1 from outside.

Corrected rule, applied to OUTPUT instead:
  iptables -I OUTPUT 1 -p icmp --icmp-type time-exceeded -j DROP
  iptables -I OUTPUT 1 -p icmp --icmp-type time-exceeded -m limit --limit 1/second --limit-burst 1 -j ACCEPT

## Evidence
Final mtr result:
  1. 10.0.1.1 (router1)   10.0% loss
  2. 10.0.2.2 (server)     0.0% loss

Loss is correctly and exclusively attributed to hop 1 (the rate-
limited intermediate router), while hop 2 (the actual destination)
remains completely clean -- proving the network path itself is fully
functional and the loss is isolated to router1's own ICMP generation
behavior, not a real forwarding failure anywhere in the path.

## Real-World Relevance
- A single hop showing loss in mtr/traceroute does not by itself prove
  that hop is dropping real traffic -- always check whether traffic
  reaches every hop AFTER it (if it does, the intermediate hop simply
  isn't replying reliably, not failing to forward).
- ICMP has multiple distinct types (echo-request/reply, time-exceeded,
  destination-unreachable, etc.) that serve completely different
  purposes. A firewall rule written for one type has zero effect on
  another, even though both are "ICMP."
- Traffic a host generates itself (like automatic time-exceeded
  replies) is OUTPUT, not INPUT, from that host's own perspective --
  a common and easy mistake when writing firewall rules meant to
  affect a host's own generated responses.
